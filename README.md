# ЛР №4. Подсчёт объектов в видео — вариант 16 (car, stride 5)

**Автор:** Наздратенко Илья, СибАДИ, группа ПИб-23Э1.
**Дисциплина:** Системы искусственного интеллекта, 4 курс. Связь с лекцией №6 «Системы видеоаналитики».

## Что делает проект

Простой конвейер видеоаналитики: из видео берётся каждый 5-й кадр, YOLO ищет на нём автомобили, считается среднее и максимальное число машин на обработанный кадр, результат сохраняется в `report.json`, а кадры и видео с рамками — рядом. Трекера нет, поэтому число уникальных машин не определяется (`unique_tracks: null`, см. раздел 6).

```
видео → каждый N-й кадр → YOLO (класс car) → подсчёт → report.json + кадры/видео с рамками
```

Дополнительно есть веб-интерфейс с прогрессом (раздел 8). Он только запускает тот же CLI подпроцессом, так что результаты в вебе и в консоли совпадают.

## 1. Быстрый старт

Нужны Python 3.10+ и желательно `ffmpeg` (для видео с рамками в H.264; без него видео остаётся в mp4v и может не играть в браузере).

```bash
python -m venv .venv
source .venv/bin/activate          # Windows: .venv\Scripts\activate
pip install -r requirements.txt
python -m src.count_video --source data/sample.mp4 --class car --stride 5
```

Результаты появятся в `outputs/sample/`: `report.json`, `run_info.json`, `annotated.mp4`, `frames/*.jpg`, `run.log`. Проверка отчёта: `python scripts/check_report.py outputs/sample/report.json`.

Замечания:
- Веса `yolov8n.pt` при первом запуске скачает ultralytics с GitHub в папку `models/` (в репозитории весов нет). Нужен интернет один раз.
- На Linux `pip install -r requirements.txt` ставит PyTorch с поддержкой CUDA (несколько ГБ). Если GPU не нужен, поставьте CPU-сборку той же версии до остальных зависимостей: `pip install torch==2.9.1 torchvision==0.24.1 --index-url https://download.pytorch.org/whl/cpu`.
- Запуск без аргументов (`python -m src.count_video`) использует значения варианта 16: `data/sample.mp4`, `car`, `stride 5`.

## 2. Аргументы CLI

| Аргумент | По умолчанию | Описание |
|---|---|---|
| `--source` | `data/sample.mp4` | путь к видео |
| `--class` | `car` | имя класса COCO; проверяется по `model.names` |
| `--stride` | `5` | обрабатывать каждый N-й кадр, целое ≥ 1 |
| `--out` | `outputs/<имя_видео>` | папка результатов |
| `--model` | `yolov8n.pt` | веса; сначала ищутся в `models/`, иначе их скачает ultralytics |
| `--conf` | `0.25` | порог уверенности |
| `--imgsz` | `640` | размер входа YOLO (значение по умолчанию берётся из `YOLO_IMGSZ`) |
| `--save-frames` | `8` | сколько кадров с рамками сохранить (0 — не сохранять) |
| `--no-video` | выкл. | не писать видео с рамками |
| `--progress-json` | нет | служебный: файл прогресса для веба |
| `--quiet` | выкл. | меньше логов |

Коды выхода: `0` успех; `2` неверные аргументы (например, `--stride 0` или неизвестный класс — с перечнем доступных); `3` файл не найден, не открывается или в нём нет кадров; `130` прерывание (Ctrl+C), при этом недописанные файлы не остаются, а `report.json` пишется атомарно.

Лог выводится в консоль и в `run.log` в формате `ЧЧ:ММ:СС | уровень | сообщение`: параметры старта, каждые ~10 % или 20 обработанных кадров строка «обработано / пропущено / ETA», в конце итог «всего кадров, обработано, пропущено, stride, время».

## 3. Формат `report.json`

Ровно 10 ключей в порядке из ТЗ:

| Поле | Значение |
|---|---|
| `source` | путь к видео, как передан в `--source` (слеши прямые) |
| `class_name` | класс COCO |
| `stride` | шаг отбора кадров |
| `frames_total` | реальное число кадров, пройденных `read()/grab()`, а не значение из метаданных контейнера |
| `frames_processed` | кадров, отправленных в YOLO; всегда `ceil(frames_total / stride)` |
| `detections_per_frame_mean` | среднее число машин на обработанный кадр (по обработанным, не по всем), 2 знака |
| `detections_per_frame_max` | максимум машин на одном обработанном кадре |
| `unique_tracks` | всегда `null`: трекера нет |
| `model_version` | `"v1.0"`, как в образце ТЗ и теге релиза |
| `elapsed_sec` | время от начала цикла кадров до записи последнего выходного файла, без загрузки модели |

Фактические веса, версии библиотек, fps, разрешение, `model_load_sec`, пик памяти и число машин по каждому обработанному кадру лежат в `run_info.json`: так формат `report.json` остаётся ровно таким, как в ТЗ. Реальный пример — в разделе 4.

Считается ровно класс COCO `car` (id 2). Грузовики, автобусы и мотоциклы — другие классы и в счёт не входят.

## 5. Почему stride = 5

**Стоимость.** Время ≈ `(frames_total / stride) × t_кадра + t_ввода-вывода`. При stride 5 в YOLO уходит в 5 раз меньше кадров, чем при обработке каждого, а инференс — главная цена на слабом CPU. Пропущенные кадры всё равно проходят через декодер (для межкадровых кодеков это неизбежно), поэтому экономия чуть меньше идеальной.

**Риск.** Любое событие, непрерывно видимое не менее `stride` кадров, гарантированно попадёт хотя бы в один обработанный кадр. При 30 кадр/с и stride 5 это 5/30 ≈ 0,17 с. Автомобиль в кадре обычно виден секундами, поэтому пропустить машину «целиком» маловероятно. Но события короче 0,17 с (быстрое пересечение края кадра, мерцание детекции) могут потеряться, а динамика между обработанными кадрами не видна.

**Компромисс.** Stride 5 даёт 6 анализов в секунду при 30 fps: достаточно для оценки плотности движения и дёшево для учебного CPU. Для быстрых объектов или точного подсчёта нужен меньший stride вместе с трекером; для длинного видео на слабом железе — больший. Для другого fps: анализов в секунду = `fps / stride`, окно риска = `stride / fps` секунд.

**Эксперимент.** Те же параметры, кроме stride; основной запуск остаётся со stride 5 (по варианту), остальные значения нужны только для сравнения. Полная таблица и условия замера — в [docs/stride_experiment.md](docs/stride_experiment.md).

## 6. Ограничения простого счётчика и `unique_tracks: null`

1. `detections_per_frame_mean` и `detections_per_frame_max` — это среднее и максимум числа машин **в одном кадре**, а не число разных машин в видео.
2. Одна и та же машина, видимая на 30 обработанных кадрах, учтена 30 раз: без трекера её нельзя отличить от 30 разных. Поэтому по этим числам **нельзя** судить о пропускной способности дороги или числе проехавших машин.
3. `unique_tracks = null` означает «не измерялось», а не «ноль машин».
4. Детектор может пропустить мелкие, далёкие и частично закрытые машины и ошибаться при плохом свете. Считается только класс COCO `car`: грузовики, автобусы и мотоциклы не входят.
5. Из-за stride 5 кадры между обработанными не анализируются совсем.
6. Для настоящего подсчёта уникальных машин нужен трекер (например, ByteTrack) и линия пересечения; это вне объёма работы.

## 8. Веб-демо

Необязательная часть: страница, где можно загрузить видео и следить за прогрессом (отправка файла, подготовка модели, кадры, сборка результата), потом посмотреть метрики, график, кадры, видео, `report.json` и скачать всё архивом. Есть кнопки «Попробовать на примере» и «Посмотреть готовый результат примера» (последний показывает файлы из `examples/sample/` мгновенно).

```bash
uvicorn app.main:app --port 10000      # затем открыть http://localhost:10000
```

Устройство: FastAPI (один воркер) запускает `python -m src.count_video ... --progress-json` подпроцессом и читает его прогресс; веб-процесс не импортирует torch. Одновременно идёт одна обработка (вторая получает 409). Лимиты задаются переменными окружения: `MAX_UPLOAD_MB=25`, `MAX_DURATION_SEC=60`, `MAX_WIDTH=1920`, `JOB_TIMEOUT_MIN=45`. Результаты хранятся в `/tmp/jobs/` и удаляются через 30 минут после завершения.

## 9. Деплой на Render через Blueprint

1. Загрузите репозиторий на GitHub (см. раздел 14).
2. В Render: **New → Blueprint**, выберите репозиторий, нажмите **Apply**.
3. Дождитесь сборки Docker-образа и откройте выданный URL.

Файл `render.yaml` лежит в корне: бесплатный `web`-сервис в регионе Frankfurt, `healthCheckPath: /api/health`. Поля сверены с документацией Blueprint Spec, но проверка по JSON-схеме Render не выполнялась (доступа к ней не было).

Особенности тарифа Free (0,1 CPU, 512 МБ RAM):
- сервис засыпает через 15 минут без трафика и просыпается около минуты; пока вкладка открыта и опрашивает сервер, он не засыпает;
- файловая система эфемерная: после перезапуска всё пропадает, поэтому результаты нужно скачивать сразу;
- скорость в разы ниже, чем на ноутбуке (порядок — секунды на кадр), поэтому лимит на обработку 45 минут;
- главный риск — память, см. раздел 10.

## 10. Проверка на тарифе Free

**Сборка Docker-образа и запуск с лимитами не выполнялись**: в среде, где собиралась работа, нет доступа к реестру Docker и к `download.pytorch.org`. Поэтому Dockerfile проверен только чтением, а сборка — нет. Проверьте у себя:

```bash
docker build -t sii-lr04 .
docker run --rm -m 512m --cpus 0.1 -p 10000:10000 sii-lr04
# в другом окне: загрузить data/sample.mp4 через http://localhost:10000
# замер пика памяти: docker stats  (или смотрите peak_rss_mb в run_info.json результата)
```

Что измерено реально (Linux x86_64, 2 vCPU, 8 ГБ, Python 3.11, torch 2.9.1 **CUDA-сборка** с PyPI, так как CPU-сборка была недоступна):
- веб-процесс (uvicorn без torch) занимает около 56 МБ RSS;
- процесс обработки: `import torch` ≈ 600 МБ RSS, весь процесс с моделью и инференсом на `yolov8n.pt` — пик 700–830 МБ в разных замерах; `imgsz` 640 → 480 → 320 экономит лишь 10–20 МБ;
- около 240 МБ из этого — файлы библиотек CUDA и triton, которых в CPU-сборке нет.

Вывод: на CPU-сборке пик, по грубой оценке (не измерению), будет порядка 550 МБ, то есть **вплотную к лимиту 512 МБ или выше**. Вполне возможно, что на Render Free обработка упрётся в память: веб-страница в этом случае покажет «Не хватило памяти на бесплатном тарифе», а сам сервер останется жив, потому что обработка идёт в отдельном процессе. Лестница отступлений: уменьшить `imgsz` (`YOLO_IMGSZ=480`, затем `416`), затем ограничить ширину входа (`MAX_WIDTH`), либо взять платный тариф. Основной результат работы — CLI, он от этого ограничения не зависит.

## 11. Тесты и CI

```bash
pip install -r requirements-dev.txt
ruff check .
pytest -m "not integration"
```

Тесты идут на подставном детекторе, без torch и без скачивания весов: проверяют отбор кадров 0, N, 2N, … и инвариант `frames_processed == ceil(frames_total / stride)` (stride 1, stride больше длины видео, видео из одного кадра), формат `report.json` (ровно 10 ключей), коды выхода CLI, прогресс и веб-API. Тест с реальным YOLO помечен `integration` и пропускается, если нет весов или sample. CI (`.github/workflows/ci.yml`) ставит только лёгкие зависимости и запускает `ruff` и `pytest` на Python 3.10 и 3.11.
